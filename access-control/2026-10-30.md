# Access Control（アクセス制御） — 2026-10-30

## このトピックは何か
「あなた、それやっていい人？」をサーバーが確認する仕組み。
Webの守りは3段構え：
- 認証（Authentication）… 誰か？（ログイン）
- セッション管理（Session management）… さっきの人と同じか？（Cookie）
- アクセス制御（Access control）… その操作をする権限があるか？

Path traversal が「どこ（What）」の問題なら、Access control は「だれ（Who）」の問題。

## 解いたラボ（3つ）
### 1. Unprotected admin functionality ✅
- `/robots.txt` に `Disallow: /administrator-panel` とヒントが漏れていた。
- その `/administrator-panel` に一般ユーザーのまま直アクセス → 管理パネルが開いた。
- carlos を Delete して解決。Burpすら不要、URL直打ちだけ。

### 2. Unprotected admin functionality with unpredictable URL ✅
- 管理パネルのURLが `/admin-7ct62s` と推測しにくい形（security by obscurity）。
- でもページのJavaScript内に `adminPanelTag.setAttribute('href', '/admin-7ct62s')` と書いてあった。
- `isAdmin=false` でリンクは画面に出ないが、JSのコード自体は全員に配られるのでURLが丸見え。
- そのURLに直アクセス → carlos削除。

### 3. User role controlled by request parameter ✅
- wiener:peter でログイン。Cookieに `Admin=false` がサーバーから付いてきていた。
- `Admin=false` → `Admin=true` に書き換えて `/admin` にアクセス → 管理パネルが開いた（200 OK）。
- Responseの中に `<a href="/admin/delete?username=carlos">` を発見。
- `GET /admin/delete?username=carlos`（Admin=trueのまま）を送信 → carlos削除。

## 自分の言葉での理解
- 「隠す・URLを変える」は対策にならない（security by obscurity）。
  robots.txt、JS、Wayback Machine など、隠し場所はいずれバレる。
- 本物の対策は「場所を隠す」じゃなく「来た人の権限を確認する」。単純に聞けばいい。
- HTTPはステートレス（前を覚えてない）。各ページが毎回Cookieを見て「誰か」を判定する。
  → 毎回チェックが必要 = どこか1ページ書き忘れる = そこが穴になる。
- ラボ3の罠：チェック自体はしていた。でも判定材料の `Admin` をユーザーが触れるCookieに置いた。
  「守ろうとしたのに、守りの材料を敵に渡していた」。
  正しくは、権限はサーバー側だけが持つ記録（ユーザーが触れない場所）で判断する。
- administratorに「なった」わけではない。身分はずっとwienerのまま。
  サーバーが権限をAdminの値だけで判断していたので、値を偽ってサーバーを騙しただけ。

## 縦と横の権限昇格
- 縦（vertical）… 一般ユーザー → 管理者（上の権限を取る）。今日やったのは全部これ。
- 横（horizontal）… ユーザーA → ユーザーB（同じ立場の他人になりすます）。
  例：`?id=carlos` で他人の情報を見る。これは次回テーマ。

## リクエストの部品（GET /admin/delete?username=carlos HTTP/2）
- GET … メソッド。「ちょうだい」（見る・取る）。POSTは「送る」。
- /admin/delete … パス。「どこの機能か」（管理エリアの削除機能）。
- ?username=carlos … クエリパラメータ。「対象は誰か」。`?項目=値` で処理対象を指定。
- HTTP/2 … 通信の規格バージョン。気にしなくてよい。

## 全ラボ共通の構造（今日の一番の収穫）
```
理想（守ったつもり） → 現実は実装で1ヶ所抜ける → 攻撃者はその1ヶ所を突く
攻撃の型：①理想を知る ②疑う（ちゃんとやってる？漏れは？）③抜けを突く
```
脆弱性の正体 = 「考え方の穴」ではなく「実装の抜け」。
バグバウンティで報酬が出るのは、ほぼ全部ここ。

## メタ読みについて（自分の気づき）
- URLの形を先読みする（例：`delete?username=carlos`）のは良い癖。でも「メタ読みで終わり」はワナ。
- 外したとき気づけない／トークン（CSRF等）が必要な場合がある。
- 正しい順番：メタ読み → 確認（ソース/Responseで実物を見る）→ 実行。
