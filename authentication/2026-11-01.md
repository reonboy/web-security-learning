# Authentication（認証の脆弱性） — 2026-11-01

## 認証 vs 認可（AuthN / AuthZ）
- Authentication（認証, AuthN）= 「誰か？」本人確認（ログイン）。
- Authorization（認可, AuthZ）= 「それをしていいか？」権限確認。
- 順番：まず①認証（誰か）→ ②認可（何していいか）。
- これまでの Access control は②認可を破っていた（本人だが権限を越えた）。
  Authentication は①認証そのもの（本人じゃないのに入り込む）を破る。

## 総当たり（Brute-force）の基礎
- 完全ランダムではなく、公開情報・よくあるパスワードで候補を絞る「賢い総当たり」が実戦。
- 漏洩リスト（rockyou.txt 等）/ credential stuffing（使い回しを突く）が強力。
- ユーザー名も総当たりの対象。先に「有効なユーザー名」を特定 → そのパスワードを総当たり、の2段構え。
- Username enumeration = サイトの反応の違い（エラー文・Length・Status・速度）から「実在するユーザー名」を見分ける。
  まともなサイトは「ユーザー名またはパスワードが違います」と曖昧にして、どちらが違うか教えない（これが正しい守り）。

## 解いたラボ
### Username enumeration via different responses ✅（初 Intruder）
- ログイン通信（POST /login, username=§x§&password=test）を Intruder へ。
- ユーザー名リスト101個を Payloads に Paste → Start attack。
- 1個だけ Length が違う（他 3352、ap だけ 3354）→ 有効なユーザー名 = `ap`。
- 次に username=ap 固定、password=§x§ でパスワードリスト100個を総当たり。
- 1個だけ Status 302 / Length 184 → 正解パスワード = `555555`。
- ap / 555555 でログイン → 解決。
- ※ Burp Community の Intruder は激遅（待ちが長い）。本気は Professional か Hydra/ffuf。

### 2FA bypass ✅
- carlos:montoya でパスワードまでログイン（①完了、2FAコード画面へ）。
- コードを入れずに、ログイン後ページ（/my-account?id=carlos）へ直接アクセス → 入れた。
- サイトが「②を終えたか」を確認していなかった（無防備パネルと同じ骨格）。
- 失敗例：wiener で完全ログイン → そこに carlos の Cookie を「混ぜる」はダメ。
  Cookie は1本で1人。混ぜられない。carlos 単独で①まで進むのが正解。

## 見るべき数字（Intruder）
- Response received（時間）→ 揺らぐのが当たり前。無視。
- Length（文字数）→ 他と違う1個を探す（username enumeration で使う）。
- Status code → 302 を探す（ログイン成功の合図）。

## 原則
- Never trust user input（ユーザー入力を信用するな）。届く時点で全部改ざんされうる。
