# File Upload（ファイルアップロードの脆弱性） — 2026-11-01

## このトピックは何か
画像アップロードなどの機能に、画像のフリをしてサーバーサイドスクリプト（PHP等）を送り込み、
サーバーに実行させる攻撃。成功すると RCE（リモートコード実行）= サーバー完全支配。報酬最高額クラス。

## Web シェル
- Web shell = HTTPリクエストを送るだけでサーバー上の任意コマンドを実行できる悪意あるスクリプト。
- ファイルを読むだけ：`<?php echo file_get_contents('/path/to/file'); ?>`
- 何でも実行できる万能版：`<?php echo system($_GET['command']); ?>`（例：exploit.php?command=id）
- 2段階：① ファイルを上げる（まだ実行されない）→ ② そのファイルのURLにアクセスして実行。

## 解いたラボ
### Remote code execution via web shell upload（検証なし） ✅
- 検証が一切ないので .php をそのまま上げられた。
- `<?php echo file_get_contents('/home/carlos/secret'); ?>` を aiueo.php として保存・アップロード。
- アップロード先 avatars/aiueo.php のURL（/files/avatars/aiueo.php）にアクセス → secret が返る。
- ゴールが「1ファイル読むだけ」なら file_get_contents 版がシンプル（system版はオーバースペック）。

### Web shell upload via Content-Type restriction bypass（甘い検証） ✅
- サーバーは Content-Type が image/jpeg か image/png かだけをチェック（中身は見ない）。
- .php を上げると Content-Type: application/octet-stream で弾かれた。
- Burp で multipart のファイルパーツの `Content-Type:` を image/jpeg に書き換え → 通った。
- 中身（<?php ...?>）は触らず、札（Content-Type）だけ書き換える。

## 自分の言葉での理解
- Content-Type は「送信者の自己申告の札」。サーバーが調べた結果ではない → 書き換えられる → 信用してはいけない。
  （前回の Admin=true と同じ構造。Never trust user input。）
- 正しい検証は、札ではなく中身（マジックナンバー＝ファイル先頭のバイト）を見る。
- multipart/form-data の1パーツの構造：
  - Content-Disposition（宛名：どの入力欄か＋filename）
  - Content-Type（種類の札）← 書き換える的
  - （空行）
  - 実際の中身（<?php ...?>）← 触らない
- ブラウザの見た目（Not Found）に惑わされない。Burp の通信ログが真実。
  アバター画像として自動読み込みされる＝ページを開くたびに aiueo.php が実行され、Burp に secret が記録される。

## 対策（きりがないブラックリスト問題）
- ブラックリスト（禁止リスト）はきりがない・漏れる → ホワイトリスト（.jpg .png だけ許可）にする。
- さらに多層：② 中身検証（マジックナンバー）③ リネーム ④ 実行できない場所に保存（← 入っても害が出ない、最強）。
- 思想：入り口で全部弾くのは無理 → 入っても実行させない設計にする。

## 脆弱性チェーン（自分の気づき）
- 完璧に実装されていれば File upload 単体はほぼ詰み。
- でも実戦では「適用のムラ」で必ずどこか漏れる。
- Path traversal × File upload が強い連鎖（ファイル名に ../ を仕込み、実行できる場所に保存先をずらす）。
